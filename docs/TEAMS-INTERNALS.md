# Microsoft Teams internals (summary)

Findings from studying a live, signed-in Teams (teams-for-linux, Teams v2 web,
2026-09-23–24) through CDP. These are undocumented internals; `teams-cli doctor`
re-checks core cache/composer contracts, not every event schema or file viewer.

## Data access

The implementation reads Teams' local IndexedDB/DOM data and passively observes
traffic generated by the application. Observation is scoped to a command and
projects selected fields rather than retaining headers or credentials. Writes
use the Teams interface.

Independent requests to Teams/Microsoft services using credentials extracted
from the page are outside the project's supported access model.

## Cache and UI observations

- **Local cache**: one IndexedDB database per "manager", per account and locale. Used:
  `conversation-manager` (conversations, read horizons) and `replychain-manager`
  (messages, reactions summary). Also present: `activity-manager` (mentions, replies,
  reactions, with read state), calendar stores (empty: the calendar is Outlook's),
  an offline-actions queue.
- **Freshness**: new and edited messages reach the cache within ~100 ms, pushed by
  Teams' own real-time channel. That timing was one observation, not a guarantee. `wait` now arms observation
  before the cache baseline and uses events to wake cache checks.
- **UI**: React + CKEditor 5; stable hooks are `data-tid`, `data-mid`, pane header ids
  and send buttons tagged with the thread id. The left rail is a recency-limited list.
- **User activity signals**: window focus, visibility, and the open composer's content.
- **Attachments**: messages carry file metadata (name, type, SharePoint location) and
  inline image references; the content itself lives in Microsoft services.
- **Service traffic** runs in web workers; observing it passively needs attaching to
  those workers.


## UI and observation details (2026-09-24)

- A UI send produces a worker-side `201` response with the server message id in
  `Location`. Its outgoing `clientmessageid` matches `clientMessageId` in IndexedDB.
  `send` now requires that correlation plus full normalized text equality.
- The reaction portal carries `<messageId>-popover-surface`; its Tabster modalizer
  independently carries `<messageId>-Main`. Both are checked before reacting.
- Trouter uses Socket.IO-style `3:::` frames containing JSON whose `body` is another
  JSON string. `type` is `EventMessage`; `resourceType` distinguishes `NewMessage`
  from `MessageUpdate`. Reaction changes were observed as `MessageUpdate`.
- The calendar is an Outlook iframe with its own worker. Teams' UI navigation loaded
  `GetCalendarView` responses with `Body.Items`, `ResponseCode`, `ResponseClass`.
  `calendar` now selects this exact operation, with range/calendar/timezone from its
  business-data header `x-owa-urlpostdata`. `Network.getResponseBody` reads the already
  completed response after `loadingFinished`. A private personal appointment without
  attendees/reminder was created through the UI, read successfully, deleted through
  the UI and confirmed absent. No appointment fixture remains.
- A SharePoint attachment tile carries its zero-based index, filename and object path.
  Opening with Enter loads an `embed.aspx` viewer, then `download.aspx?UniqueId=...`.
  The full response is matched to the cached SharePoint id and origin. A thumbnail
  uses a separate route and is not the file. An existing self-chat Markdown attachment
  was read and exported with matching byte counts; its metadata/output remained fenced. No upload
  was needed. `attachments --read` supports this full-response viewer path; range-only
  and other viewers fail explicitly.

### Event schemas: loaded source evidence versus live observations

The following adapters were derived from static scripts already loaded by Teams,
read through `Debugger.getScriptSource`. The parser tests use synthetic values with
those shapes; they are not recordings of real incoming calls or other people's typing.

- `precompiled-web-worker-inner~c-5552f1dedb09fde0.worker.js`: the presence listener
  parses `body.presence` as one entry or an array. The presence manager in
  `precompiled-web-worker-inner~b-1b68586193a5f9cd.worker.js` consumes
  `{mri, etag, presence: {availability, activity}}`. Only these fields are projected;
  status notes/calendar data are excluded. Two passive live windows (30s/55s) received
  no presence events, so there is no positive end-to-end presence sample yet.
- The typing manager handles the exact `Control/Typing` message type, extracting
  `conversationid` or the conversation link and sender MRI. Arrival/version identifies
  pulses; no inferred “stopped typing” event is emitted. No live typing sample yet.
- `cmd-trouter-c09e25d038cb2178.js` reads `evt`/`eventId` from the parsed body.
  `calling-pluginless-a75c845ab3a1f615.js` recognizes incoming event ids
  107/109/111/119/125/126 and reads `gp` (object or base64 UTF-8 JSON) or `cp`
  (base64 zlib/gzip). Projection keeps call id, thread id, caller identity and call type;
  it discards signaling links, participant/debug data and credentials. Compressed
  expansion is bounded. Call history and meeting-start notifications are not treated
  as incoming calls. No live call was induced.
- Message creation/update and outgoing `201` correlation have positive live evidence.
  Loss of CDP, target detachment, and a recognized push socket closing are explicit
  errors. A socket that predates attachment can only be identified once it emits a
  recognized event. Unknown schemas are ignored; an empty `watch` is only “no matching
  decoded event in this window”, not proof that the server had no activity.
- The transport follows CDP's related-target recursive attachment and acknowledges
  `Network.enable` before resuming new workers. See the official
  [Target protocol](https://chromedevtools.github.io/devtools-protocol/tot/Target/)
  and [Network protocol](https://chromedevtools.github.io/devtools-protocol/tot/Network/).
